## 2. `ingest/mailrules.py` — 822 lines — **KEEP, but stop patching by denylist**

Deterministic email classification. Pure functions, no I/O, no LLM.

### Needed
- `classify_scored()` — weighted keyword scoring, subject counts ×2. Sound design.
- `parse_company_role()` — company/role extraction with a sensible precedence
  chain (subject patterns → sender display → sender domain → body → Workday
  tenant URL).
- `advance_status()` — **correct and important**: funnel is forward-only and
  `rejected` is terminal, so a late "application received" cannot undo an offer.
- `normalize_company()` / `best_company_match()` — uses stdlib `difflib`, no
  fuzzy-match dependency. Good call.
- `ATS_DOMAINS` / `JOB_DOMAINS` — domain→platform, load-bearing.

### Not needed / smells
- **`NEWSLETTER_DOMAINS` is a denylist of symptoms.** It contains `github.com`,
  `gitlab.com`, `bitbucket.org`, `leetcode.com`, `coursera.org`, `educative.io`,
  `thinkific.com`, and **`eatclub.in` (a food-delivery service)**. Every entry
  was added to suppress one observed false positive. The list can never be
  complete; any new newsletter domain re-opens the same bug class.
- **Six special-case layers in the classifier**, each documented as a past
  incident: `_strip_conditional`, `_strip_jd_assessment`, `_NON_EMPLOYMENT_OFFER`,
  `_INTERVIEW_DIRECT` gate, `_OFFER_DIRECT` gate, subject-authority override.
- `domain_platform()` and `score_signals()` are **test-only**.

### Root cause
Precision is being bought with hand-maintained exceptions rather than the one
structural fact that actually separates application mail from everything else:
**an application-status email belongs to a thread for an application you
submitted.** Sender-domain and keyword heuristics are being asked to infer that
relationship instead of using it.

### Fix / modularity
1. Prefer **thread linkage** over keywords where available: `inbox.py` already
   computes `thread_id` and `_link_job`. A message that cannot be tied to a known
   application or ATS thread should need a much higher bar.
2. If the denylist stays, move it to config/data so adding a domain is not a code
   change and a released version.
3. `_WEIGHTED_RULES` is already clean data — leave it.

## 2b. `ingest/inbox.py` — 792 lines — **KEEP, split `_process_uid`**

IMAP ingestion. The I/O half; all judgement lives in `mailrules`.

### Needed — and notably well built
- **Never mutates the mailbox**: `readonly=True` + `BODY.PEEK` everywhere. Stated
  in the docstring and actually honoured throughout.
- **UIDVALIDITY epoch detection.** When Gmail resets UIDs, `_sync_folder` detects
  the change, replays `uid_recovery_days`, and marks health `recovered` instead
  of silently missing mail. This is a subtle correctness problem handled properly.
- `_search_uids` correctly filters `n:*`, which always returns at least the
  highest message even when nothing is new.
- Retry with exponential backoff capped at 2.0 s; per-message `try/except` so one
  malformed message never sinks a run; `set_source_health` at every failure path.
- `_link_job` → fuzzy company, then exact role, else a stable
  `mail:<sha1>` synthetic id so email-only applications still dedupe.
  (This is why the NTT application is `job_id='mail:cbd5dc475f84'`.)

### Fix / modularity
- **`_process_uid` has ~9 responsibilities**: header fetch, noise gate,
  transactional gate, campaign-reply detection, provider-feedback (bounce)
  classification, opt-out detection, company/role parse, job linking, event
  upsert + application mutation. It is the hardest function in the repo to
  reason about, and it is where the funnel-corruption bugs have landed.
  Extracting the gate chain (`_should_ingest(...) -> bool`) would isolate the
  part that has repeatedly broken.
- **Inbound is coupled to outbound.** `inbox.py` reaches into
  `jobscope.apply.campaigns` (`classify_provider_feedback`, `is_optout_text`) and
  `jobscope.apply.outreach` (`valid_company_recipient`) via inline imports. Reading
  your mail should not depend on the campaign feature existing.
- `store_snippets` defaults to **False**, so message bodies are not retained.
  Two consequences: reconciliation must stay conservative (see below), and a
  "last message from them" UI is impossible without a config change.

## 2c. `ingest/reconcile.py` — 420 lines — **KEEP ALL. Best code in the repo.**

Rebuilds the funnel from the mail timeline. Two passes: `reclassify` (re-check
stored events against current rules) and `recompute` (rebuild statuses).

### Why it earns its complexity
- **`split_instances()`** solves a real problem correctly: one rejection must not
  collapse a company where you have other or later applications. A positive event
  after a rejection starts a new instance (re-application); a distinct role gets
  its own instance.
- **Full audit trail with recoverable tombstones.** `begin_reconciliation_run` →
  `_append_reconciliation_decision(...)` → `_tombstone_application(..., recoverable=True)`.
  Nothing is hard-deleted; every automated decision is recorded with a reason code.
- **`reconciliation_exempt`** lets a row be pinned against automated repair.
- **Idempotent**: events regroup by base job id with the `#n` suffix stripped, so
  re-running produces identical instances and no churn.
- **Conservative by design**: a terminal event is only demoted when the body
  snippet was retained — "a real interview whose cue lived in a body we no longer
  store must never be silently dropped."

This is over-engineered for a personal tool *in the abstract*, but it is exactly
proportionate to the asset: 121 irreplaceable applications and a history of
funnel-corruption incidents. **Do not simplify this module.**

### Fix / modularity — the one real smell
`reconcile` reaches into six **private** store methods:
`_finalize_reconciliation_run`, `_tombstone_application`,
`_append_reconciliation_decision`, `_update_mail_event`, `_delete_mail_event`,
`_set_application` — plus `from .inbox import _synthetic_job_id` (a private
function in another module, imported inside a function body).

That is the wrong boundary: either these belong to a public reconciliation API on
the store, or `reconcile` belongs inside the store package. As written, any store
refactor silently breaks the most safety-critical module in the codebase, and the
underscore convention actively misleads.

## 2e. ⚠ THE BIG ONE — the same pipeline is implemented **four** times

"Resolve a company → fetch its board → filter → score → persist" exists in four
separate places, each subtly different:

| # | Implementation | Filters | Scores | Persists | Reconciles |
|---|---|---|---|---|---|
| 1 | `ingest/ats.py::run()` | `filter_profile_jobs` | ✗ (scored later by `match`) | ✓ | ✓ `reconcile_open` |
| 2 | `apply/scout.py::scout()` | `filter_profile_jobs` | ✓ `score_jobs` | optional (`save`) | ✗ |
| 3 | `apply/monitoring.py::resolve_company()` | `filter_profile_jobs` | ✓ `score_jobs` | ✗ (preview) | ✗ |
| 4 | `ingest/monitor.py::scan_monitor()` | `filter_profile_jobs_with_funnel` | ✓ `score_jobs` | ✓ | ✓ `reconcile_monitor_jobs` |

Only #4 collects the funnel counts. Only #1 and #4 reconcile. #2 and #3 are
near-duplicates that differ mainly in whether they save. **This is why the UI
"Add company" and "Find jobs" behaved so differently** — they call #3 and #4's
cousins, not one shared function.

**Fix:** one `company_pipeline(cfg, store, company, *, persist, reconcile, funnel)`
that the four callers parameterise. This is the single highest-value refactor in
the codebase and would remove several hundred duplicated lines.

#### Correction 2026-07-29 — it is three, and the payoff is much smaller
Traced the callers before refactoring:

- `cmd_scan` → `scrape.run` → `monitor.scan_active_monitors` → **#4**.
- **#1 `ats.run()` has no production caller at all.** Its only callers are
  `cli/selftest.py` and `tests/test_ats.py` (8 call sites). The config-driven
  batch fetch it implements was superseded by `companies seed` → monitors → #4;
  `search.companies` still matters, but as seed input, not as a fetch path.
- #2 and #3 are ~45-70 lines each and genuinely differ downstream (#2 scores the
  *whole* board and marks out-of-profile entries Skip; #3 scores only candidates
  and never persists).

The actually-shared sequence is `fetch → filter → hydrate → score` — about six
lines per site, not several hundred. A `company_pipeline(...)` with
persist/reconcile/funnel flags would be a four-flag function with 16 possible
combinations and 4 real ones, which is a worse artifact than the duplication it
removes. **Revised recommendation:** delete production-dead #1 (and its selftest
hook), and leave #2/#3/#4 alone unless their *behaviour* needs to converge. The
UI divergence this section blamed on duplication was really §2f — fixed below.

**Done 2026-07-29.** `ats.run()` and the `store.reconcile_open()` it exclusively
owned are gone (−116 lines net). Four tests were deleted rather than rewritten
because `test_monitor_scan.py` already covers the same behaviour on the live path
(`test_complete_board_closes_a_missing_linked_job`,
`test_scan_monitor_failure_and_empty_board_never_close_jobs`); the two that
asserted adapter parsing were re-pointed at `fetch_company` +
`filter_profile_jobs`, and the selftest smoke check now closes a job through the
monitor path it actually uses. `search.companies` keeps its one remaining job:
seed input for `companies seed`.

## 2f. Structured data is being round-tripped through a human string

`analyze/match/scoring.py::_rationale()` builds a display string:

```python
bits = [f"top: {top}"]  ...  return " | ".join(bits)
```

`filters.apply_filters()` returns a display reason (`f"needs ~{int(req)}y experience (cap {cap}y)"`).

`ingest/monitor.py` then **parses that string back** to recover the reason the
scorer already knew:

```python
if item.rationale.startswith("needs ~"):        reason = "experience_cap"
elif item.rationale.startswith("clearance/"):   reason = "clearance"
elif " | top:" in item.rationale:               reason = "other_filter"
```

Worse, **two producers emit two different formats** for the same concept:

| Producer | Format |
|---|---|
| `analyze/match/run.py` | `f"⛔ {reason} \| {r}"` — emoji-prefixed |
| `analyze/review.py::score_jobs` | `f"{reason} \| {rationale}"` — no prefix |

`monitor.py`'s `startswith()` checks only work because it happens to consume the
second format. Any consumer of the first would silently bucket everything as
`below_threshold`. **Fix:** have `apply_filters` return `(code, message)` and
carry the code through `ScoredJob`. Small change, removes a whole fragility class.

#### FIXED 2026-07-29
`apply_filters` now returns `(code, reason)`; `ScoredJob` carries `skip_code`; and
`scan_monitor` buckets on `item.skip_code or "below_threshold"` instead of parsing
sentences. The `" | top:"` catch-all became a real `off_target_title` code, so the
funnel names the actual filter rather than "Other filter". A regression test
reworded a filter message and asserts the bucket does not move.

## 3. Feature opportunities (job hunt)

### ~~F1 — "Chase" view for ghosted applications~~ — **RETRACTED**

**This finding was wrong.** I claimed `FOLLOWUP_DAYS`, `GHOST_DAYS`,
`isAwaitingReply` and `lastActivityAt` were test-only or unreferenced, and that
ghosting detection was invisible. It is neither.

The real chain is complete and shipped:

```
pipeline.ts   staleness() / followupsDue() / ghosted()   buckets fresh|due|ghosted
   -> board.ts        attaches  followup?: 'due' | 'ghosted'  to each card
   -> Board.tsx       "attention" filter + "Ghosted" chips + row grouping
   -> briefing.ts, analytics.ts also consume it
```

Ghosting and follow-up tracking already work. Cause of the error: the home-file
exclusion described in §1. Recorded here rather than deleted, so the mistake is
visible.

### F2 — Requisition-ID threading
`reconcile.py` already extracts requisition IDs from subjects and bodies
(`_REQUISITION_SUBJECT`, `_REQUISITION_BODY`, `\bref\s*:\s*\d{5,}`) and uses them
to decide canonical identity. That same ID is the strongest available join key
between *an email* and *the application it belongs to* — stronger than fuzzy
company matching. Using it earlier (in `inbox._link_job`, not just during
reconciliation) would reduce the keyword-heuristic burden described in §2.

### ~~F3 — Turn the audit trail into a visible history~~ — **RETRACTED 2026-07-29**
`reconciliation_audit` records every automated decision with a reason code and a
`recoverable` flag, and **nothing surfaces it**. "This application was moved to
Rejected on 12 Jul because of an email from X" is already stored. Showing it
would make the funnel trustworthy instead of mysterious — and it is read-only
rendering of data that already exists.

**Measured before building it, and the premise is false.** The live database holds
**1 decision row across 122 applications** (`application_tombstoned` /
`orphan_mail_application`). The table only logs *reconciliation* runs, which are
occasional and operator-triggered; it never sees the everyday status changes that
happen during inbox ingestion. Rendering it would ship an empty panel.

The underlying question — "why is this application marked Rejected?" — is already
answered elsewhere: `render._application_records` attaches a per-application
`timeline` built from `mail_events` (170 rows, 124 applications), and
`JobDrawer.tsx::ApplicationTimeline` renders it. The need is met; only the
proposed *source* was wrong.

Also worth noting: `idx_reconciliation_decisions_application` indexes
`application_id`, but no query filters on it. The index was built for the
per-application view this section imagined, and that view never arrived.

### F4 — Surface the ATS parse check  ★ high value, already built
`analyze/atscheck.py` is a genuinely strong feature that is **CLI-only**. It
reports what an ATS actually extracts from your résumé, scores ATS-friendliness
0–100, and warns with specific fixes on the things that silently auto-reject:

- image-based / scanned PDF (almost no extractable text)
- table or tab layouts (`tables`), multi-column layouts (`multi_column`)
- ligatures, box-drawing and private-use glyphs that corrupt extraction
- missing name / email / phone / skills section / experience heading

With a job id it also diffs JD keyword coverage. For someone applying at volume,
"your résumé scores 63/100 and here are the four fixes" is directly actionable —
and it is invisible unless you run `jobscope atscheck` in a terminal.

### F5 — Surface the skill-gap learning plan  ★ high value, already built
`analyze/insights.py::skill_gap` scans your Strong/Good/Stretch jobs, finds the
skills that recur in those JDs but appear in **none** of your résumés, and ranks
them by how many additional jobs each would unlock — with example companies.
That is a market-derived learning plan, and it is also CLI-only.

Both F4 and F5 need rendering, not new logic.

### F6 — Measure the ghosting deadline instead of guessing it  ★ SHIPPED 2026-07-29
`pipeline.ts` declared `GHOST_DAYS = 21` — a guess about employers in general,
applied to every application. The database can answer the question directly.

Measured on the live funnel: **11 replies, median 4 days, 90th percentile 9 days.**
Nobody who was ever going to answer took longer than about a week and a half.
Against that, the 21-day constant was leaving applications in "still worth chasing"
long after the answer had arrived as silence — **38 of 95** open applications were
labelled follow-up-worthy when the owner's own history says they were closed.

`replyWindow()` now derives the deadline from the applications that actually drew
a reply and feeds it to `staleness()`, which every consumer (board chips, the
attention filter, briefing, analytics) already routes through — so one function
corrected the whole surface. It falls back to `GHOST_DAYS` until
`MIN_REPLY_SAMPLE` replies exist, so a new user sees the generic rule and existing
tests were unaffected.

Result on the live data: window **9 days**, and all **95** open applications are
past it. That is the honest reading, and it is the argument for outreach (§4a)
stated in the owner's own numbers rather than in received wisdom.

### 4c. `apply/track.py` (468) — the digest state machine is over-built

`send_digest_result` implements a durable intent state machine —
`ready → sending → accepted | retryable | delivery_unknown` — with
compare-and-set transitions (`meta_compare_and_set`), stale-claim detection, and
a requirement to reconcile the **Sent** IMAP folder before retry (backed by
`inbox.find_sent_message`, ~60 more lines).

That is near-exactly-once delivery semantics for *emailing yourself a job digest*.

Honest trade-off: the machinery does buy something real — because `digest:last`
advances on send, a naive implementation could lose jobs from the digest forever
on a partial failure. The simpler design is *send first, advance the marker only
on success*, accepting a duplicate email on retry. That removes ~150 lines plus
the Sent-reconciliation path, at the cost of an occasional duplicate email to
yourself.

#### FIXED 2026-07-29 — the real defect was worse than the line count
Tracing the callers found a live hazard, not just excess machinery:

- `serve.py` refresh calls `send_digest_result(cfg, store)` with `retry_intent=False`.
- Any SMTP rejection parks the intent in `retryable`, which that call then refuses
  with *"digest retry requires an explicit `new --email` command"*.
- Any ambiguous outcome parks it in `delivery_unknown`, refused until somebody runs
  `new --reconcile-sent` by hand.
- Both recovery paths are **manual CLI commands**, and refresh runs digest as a
  `required=False` stage — so it reports success either way.

**One transient SMTP failure silently disabled the digest permanently.** The safety
machinery had a worse failure mode than the one it protected against.

The fix is smaller than the proposed rewrite and needs no duplicate-tolerance
argument, because `_digest_message_id` already hashes `marker + job_ids`: a resend
carries the *identical* Message-ID, so a duplicate submission collapses into one
message in the mailbox. The reconciliation edifice was guarding against something
the Message-ID had already solved. Every non-`accepted`, non-in-flight state now
retries the stored intent; a *fresh* `sending` claim still blocks, because that
attempt may genuinely be in flight.

`reconcile_digest_delivery` and `new --reconcile-sent` were left alone: no longer
load-bearing, but they still work and can still save one duplicate.

#### Found while edge-testing the fix: a one-second selection race (NOT fixed)
Writing a retry test that ran inside a single second exposed a **pre-existing**
hole, unrelated to the change above. `now_iso()` is second-resolution, selection is
`last < first_seen <= cutoff`, and the marker advances to `cutoff`. A role written
during the cutoff second, *after* `_fresh_digest_jobs` has run its query, is
therefore never sent: it missed that batch, and next time `last == first_seen` so
the strict `<` excludes it permanently.

Deliberately not fixed. Inside `serve` the refresh stages run sequentially
(scan -> match -> reviews -> digest), so nothing writes during the digest query;
the hole needs a second jobscope process committing inside that exact second. The
candidate fix -- take the cutoff one second in the past -- would add a one-second
lag and force `_pin_first_seen` into every upsert-then-send test, to close a
scenario the shipped process model does not produce. Recorded here so it is a known
bound rather than a surprise; the tests now pin timestamps instead of racing them.

**Also duplicated:** `_print_reminders` recomputes follow-up-due in Python with a
`followup_days` default of 7, while `web/src/lib/pipeline.ts` recomputes the same
rule client-side with `FOLLOWUP_DAYS = 7`. Two implementations, two places to
drift.

### 4e. `apply/apply.py` (299) — right boundary, wrong packaging

## 6. `core/ai.py` (422) — **the strongest security code in the repo**

Two mechanisms worth calling out because they are better than typical practice:

**1. Sensitive purposes are structurally barred from remote providers.**

```python
_REMOTE_BLOCKED_PURPOSES = {
    "application_answer_advice", "coverage_advice", "inbox_advice",
    "outreach_draft_advice", "tailor_advice",
}
```

Exactly the purposes that touch your résumé, your mail and your answers — the PII
surface — can only run locally. `available()` is fail-closed.

**2. `grounded_text_validator` makes fabrication structurally hard.**
Advisory output is rejected unless it shares tokens with the source, and:

- **every number** in the output must appear in the source → hallucinated metrics
  ("led a team of 12", "reduced incidents 40%") cannot survive;
- **every email** must appear in the source → no invented contacts;
- **every URL** must appear in the source → no injected links;
- prompt-injection markers are blocked outright (`ignore previous`,
  `system prompt`, `api key`, `<untrusted_data`);
- with `per_line=True`, **each sentence** must independently be grounded.

Combined with the `tailor.py` prompts that label job descriptions as data rather
than instructions (§4b), the untrusted-text path is handled properly. **Change
nothing here.**

## 9. `deliver/` — the privacy posture is genuinely strong

Three independent layers protect the published site:

1. **The public build ships nothing.** `render.build_data(public=True)` returns
   `empty_public_data()` — no jobs, no applications, no profile. All real data
   lives in an encrypted blob decrypted client-side after a passphrase.
2. **Crypto is correct.** `site_crypto.py`: PBKDF2-HMAC-SHA256 at
   **210,000 iterations**, 32-byte key, 16-byte salt, 12-byte IV, AES-GCM. That
   iteration count matches current OWASP guidance.
3. **Publish-time verification.** `publish_artifact.py` re-validates before
   release: `_validate_envelope` rejects a blob whose `kdf` isn't
   `PBKDF2-SHA256` or whose **iteration count is too low**, and `_private_markers`
   / `_serialized_markers` / `verify_artifact` scan the built assets for private
   values that must not appear publicly.

Defence in depth, and each layer is independently meaningful. Change nothing.

## 10. `enrich/` (791) — one policy concern

Nine adapters behind a `registry.py` `@source(section=…, config_key=…)`
decorator — a clean, additive plugin pattern. Each is individually toggled in

**⚠ `enrich/glassdoor.py` scrapes Glassdoor.** It fetches the Glassdoor search

prohibit automated collection. It is 33 lines, but it is **enabled by default**

Workday CXS declined, alert-link fetching ruled out). It is inconsistent with
every other decision in the repo and should be turned off by default or removed.

**RESOLVED 2026-07-29 — the scrape is gone, the useful half stayed.** Deleting the
whole module would also have deleted the one thing that worked. The rating parse
failed on essentially every call (Cloudflare), which is why the drawer rendered
`Rating: null`; the search link was never fetched-for in the first place, it was
built from the company name. So `enrich()` now returns only that link and makes
**no request at all** — verified: zero HTTP calls, `&` correctly percent-encoded.
With nothing left to rate-limit, block, or breach, it is on by default and
actually useful when researching a company before an interview.

## 13. Verdict

**This is a well-built codebase.** Seven genuinely dead symbols in 29,118 lines.
The security work is better than typical professional practice: DNS-pinned SSRF
protection, remote-blocked AI purposes for every PII path, a grounding validator
that makes fabricated numbers/emails/URLs structurally impossible, correct
PBKDF2/AES-GCM parameters verified again at publish time, an empty public build,
prompt-injection defences on untrusted job descriptions, and a reconciliation
audit trail with recoverable tombstones.

Its real problem is not quality — it is **proportion**:

- ~5,055 lines implement a compliance-grade cold-email platform that is fully
  built and **not yet switched on** (decided 2026-07-29: keep and activate — four
  config/secret blockers, no code work);
- 101 lines (`scout.py`) implement the thing actually wanted — type a company,
  see its jobs — and until today had no UI at all;
- the same company pipeline is written four times, so the two paths the UI
  exposes behave differently for no good reason.

The highest-value remaining work is **unifying four copies of one pipeline** and
**activating outreach**. Two good features that already existed — `atscheck` and
`insights` — were surfaced on 2026-07-29 and are no longer invisible.
